対象の節: $ARGUMENTS

演習ファイルは、**その節が導入する定義と主張を、読者が自分で組み直せる形に並べたもの**である。以下の基準で迷ったときは、この目的に照らして決める。

着手の条件: 同じ節の解説資料（`.html`）を先に書き、読者に読んでもらってから始める。節をまたぐ取り決めをまとめた [cross-section.md](cross-section.md) を読み、新しい取り決めが生じたら追記する。

## 1. 収録

載せるのは、その節の論理展開で役割を持つ定義・主張・節末問題である。役割で判定し、番号の有無では判定しない。定義の直後に地の文で述べられる言い換えや、定義の中に書かれた主張も、役割があれば載せる。例と Remark はこの基準の外にあり、Remark に対応する Mathlib の宣言があるときだけヘッダにその名前を書く。

## 2. 自前実装と Mathlib の使い分け

何を自前で組み、何を Mathlib のまま使うかは、**本にあるか**の一点で決める。

- その節の本文が定義または記述しているもの — 自前で組む。`my` で始まる名前を付け、本体のそのセクションに置く。定義番号のない記述（添字圏の記述、図式をその圏からの関手と見ることなど）も含む
- 前の節までに本が定義したもの — 読者が既に知っているので何も置かず、Mathlib の名前をそのまま使う。Mathlib の形が初出なら使う直前に `#check` を置く
- 本にないもの — Mathlib の道具として使う。使う直前に `#check` か `#print` を置き、本にないことと使う理由をヘッダの表に書く

Mathlib に同名のものがあるか、instance 由来かは、この判定に関係しない。

## 3. 演習の中身

自前で組むものを演習にするかは、**中身があるか**で決める。中身とは、書き下ろすと証明義務が残ること、または式や構成を自分で見つける必要があることを指す。中身があれば `sorry` を残して演習にし、なければ `sorry` なしで書き切って渡す。書き切ったものは、本の定義を Lean にしたものとして読者が読んでから演習に入る。

どこまで書いて渡すかは、**中身の所在**で決め、決定と理由をヘッダの表に書く。

- 構造が本の定義の写しに過ぎない — フィールドまで書いて渡す。演習になるのは、その定義を使う主張のほう
- 証明義務を持つ — data を書き、義務だけ `sorry` にする
- 式や構成を見つけること自体が中身 — その部分を `sorry` にする。型は必ず書く

一つの主張に複数の結論が含まれるときは結論ごとに宣言を分け、形式化が重い構成は構成とそれが満たす性質に分ける。読者が同じ分解を作り直さずに済むようにするためである。

## 4. statement の語彙と橋渡し

statement をどちらの語彙で書くかは、**Mathlib とデータの持ち方が同じか**で決める。何をデータとして持ち、何を条件として持つかがフィールド単位で一致すれば Mathlib の語彙で書き、増減していれば自前の語彙で書く。迷ったら自前側に倒す。自前実装が一つ増えるだけで、逆に倒すと節の主題が演習から消える。この判定は 3 と独立で、3 で演習にした定義でも、持ち方が一致すれば statement は Mathlib で書く。

持ち方が食い違うときは、本の定義と Mathlib の包装との橋渡しを演習にし、その直前に `#print` で Mathlib の包装を見せる。

宣言が参照するのは、原則として Mathlib のものである。自前定義を参照するのは、Mathlib に対応物がない場合に限る。

## 5. 答えの伏せ方

読者が statement や `#check` を読んだ時点で答えの形を知ってしまうものは置かず、置かない理由をヘッダの表に書く。「〜を記述せよ」「〜を特徴づけよ」型の節末問題、Mathlib の宣言名がそのまま答えになる `#check`、形式化が不自然になる問題がこれにあたる。一部だけ置けるものは、置ける部分を置いたうえで、置かない部分を同じ一覧に書く。証明の方針、ヒント、証明の途中で使う道具の `#check` も同じ理由で置かない。証明は読者が自力で書く。

## 6. 置き場所と書式

情報の置き場所は 4 つに固定する。**どの主張かは宣言の名前、形式化の判断はヘッダの表、主張とその論理構成はセクションの冒頭、Mathlib の対応物と包装は `#check`・`#print`**。散文はセクションの冒頭に限る。

宣言の名前は、本の番号を持つ主張は `<種別>_<番号>`（種別は `def`・`lemma`・`prop`・`thm`・`cor`、節末問題は `ex`。割ったときは末尾に部分を足す）、自前実装は `my` で始まる内容ベースの名前にする。`example` は使わず、ファイル内の通し番号は振らない。

ヘッダは `import` の直後に `/-! -/` で書き、次を順に並べる。

1. 節の数学的な内容は同名の HTML にある、という 1 行
2. 形式化の判断の表。universe の取り方、渡し方（3）、持ち方の差と橋渡し（4）、対応物が特殊ケースや一般化しかないときの範囲の差、対応物がないこと、本にない Mathlib の道具を使った箇所と理由
3. statement を置かない節末問題の一覧。番号と理由を 1 行ずつ
4. 載せない例と Remark
5. 参照した Mathlib のファイル名

セクションの冒頭には、本の主張を 1 文と、複数の宣言に割ったときだけ `構成:`（論理構成を宣言調で書く）を置く。各宣言の直前には、その statement と型が対応する Mathlib の宣言の `#check` を置き、必要なら `#print` を添える。`#check` には名前だけを渡し、`@` は付けない。定数名を渡した `#check` は宣言のシグネチャをそのまま表示するので、`@` を付けると universe 変数名と引数名が失われるだけになる。対応物がなければ `#check` を置かず、ヘッダの表に書く。

大見出し（本文の定義と主張、節末問題）は箱、セクション見出しは本の番号を区切り線で挟む。骨組みは次のとおり。

```lean
import ...

/-! ヘッダ -/

open CategoryTheory ...

-- ╔═════════════════════════════════════════════════════════════════════════
-- ║  本文の定義と主張
-- ╚═════════════════════════════════════════════════════════════════════════

-- ━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
-- 定義 x.y.z
-- ━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
-- 本の主張 1 文。

#check Mathlib.の.対応物

def def_x_y_z ... := sorry
```

書式の約束: 箱の右端は閉じない（全角の字送りがフォント依存で、揃えると環境によってずれる）。コメントは 1 行なら `--`、複数行なら `/- -/`。doc コメント `/-- -/` は使わず、`/-! -/` はヘッダだけに使う。

## 7. 完成の確認

作成・編集のたびに次の 3 点を確認し、通ってから完成と報告する。

- 収録漏れ — 解説資料に出てくる定義・主張・節末問題を列挙し、その一つ一つが、演習ファイルの宣言か、ヘッダの「置かない節末問題」の一覧か、「載せない例と Remark」のどれかに現れることを確認する。elaborate の検証ではこの漏れは見つからない
- Lean — `lean_diagnostic_messages` で、`sorry` 以外の警告とエラーがなく、すべての `#check` が解決し、すべての statement が elaborate することを確認する。リンタの警告はファイルの書き方で解決する。`set_option` や `lakefile.toml` でリンタを無効化して黙らせない（唯一の例外は `linter.style.header`。Mathlib の copyright ヘッダ要求は個人プロジェクトに適合しないので lakefile で無効化済み）
- 参照 — 自前定義が他の宣言から参照されていないことを確認する。参照されていれば、Mathlib に対応物がないことを確かめ、ヘッダの表に書く
