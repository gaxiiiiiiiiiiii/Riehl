対象の節: $ARGUMENTS

演習ファイルは、節を読み終えた読者が、その節の定義と主張を自分で Lean で書くためのものである。終えたとき、読者はその節の定義と主張を自分で書いており、その節の概念を以後 Mathlib の名前と形で使える。以下の基準で迷ったときは、読者がこの状態になるほうを選ぶ。

前提: 読者は同じ節の解説資料（`.html`）を読んでいる。解説資料がまだなければ、先に書いて読んでもらう。節をまたぐ取り決めをまとめた [cross-section.md](cross-section.md) を読み、新しい取り決めが生じたら追記する。

## 1. ファイルの形

骨組みは次のとおり。各部の書き方は 2〜5 で上から順に述べ、6 は書いた後の確認である。

```lean
import ...

/-! ヘッダ -/

open CategoryTheory ...

namespace Riehl

-- ╔═════════════════════════════════════════════════════════════════════════
-- ║  本文の定義と主張
-- ╚═════════════════════════════════════════════════════════════════════════

-- ━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
-- 定義 x.y.z
-- ━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
-- 本の主張 1 文。

#check Mathlib.の.対応する宣言

-- 宣言するもの 1 行
def ... := sorry

end Riehl
```

宣言はすべて `namespace Riehl` の中に置く。大見出しは「本文の定義と主張」と「節末問題」の 2 つ。コメントは 1 行なら `--`、複数行なら `/- -/`、ヘッダは `/-! -/`。

## 2. ヘッダ

`import` の直後に `/-! -/` で書き、次を順に並べる。

1. 節の数学的な内容は同名の HTML にある、という 1 行
2. 載せない例と Remark。Remark に対応する Mathlib の宣言があるときは、その名前を添える

## 3. 置くセクション

セクションを置くのは、その節の論理展開で役割を持つ定義・主張・節末問題である。定義の直後に地の文で述べられる言い換えや、定義の中に書かれた主張も、役割があれば置く。

節末問題のうち、statement を Lean で書くこと自体が解答になるもの（「〜を記述せよ」「〜を特徴づけよ」型）と、形式化が不自然になるものは、セクション見出しだけ置き、冒頭の 1 文を主張の代わりに置かない理由にする。

セクション見出しは本の種類と番号（定義 x.y.z、命題 x.y.z、演習 x.y.i など）。

## 4. セクションの冒頭

本の主張を 1 文置く。主張の文は、本が定義した形の術語と明示した量化で書き、原文が省いていれば補う。本の主張と宣言にギャップがあれば、続けて、学習が目的である読者が知るべきことを説明する。説明は statement を読むのに要ることに限る。

既存の宣言を組み合わせた項で、何を表すかが項から読めないものには、本の記法を 項 := 本の記法 で添える。関手なら対象での値 x ↦ … で書く。宣言そのものがその項なら、直上の 1 行コメントに本の記法だけを書く。

```
statement の項 := 本の記法
  curry.obj F ⋙ lim                        := i ↦ limit F(i, -)
  (Functor.const J).obj PUnit              := _ ↦ *
  yoneda.obj (limit F) ⟶ limHomFunctor F   := (X ↦ Hom(X, limit F)) → (X ↦ limit (Hom(X, F-)))

-- F ↦ (i ↦ limit F(i, -))
noncomputable def limJ : (I × J ⥤ C) ⥤ (I ⥤ C) := sorry
```

## 5. 宣言

宣言の直前に、対応する Mathlib の宣言の `#check` と、宣言するものを言う 1 行を、この順に置く。本にない Mathlib の宣言のうち、これまでの演習ファイルの statement に現れていないものは、statement に最初に現れる宣言の直前に `#check` で示す。`#check` を置くのは、この 2 つと、5.1 で主張の代わりに示す補題に限る。

一つの主張が複数の構成や等式を含むときは、それぞれを別の宣言にする。Lean が `noncomputable` を要求する定義には付ける。

### 5.1 演習と Mathlib

その節の本文が定義または記述しているものは演習にし、それ以外は Mathlib のものを使う。演習にしたものを以下では自前実装と呼ぶ。対応する Mathlib の宣言がある自前実装は、前の節のものも含めて、それより後の宣言から Mathlib の名前で参照する。本が定義するものは、読者がそれを組む演習より前の statement には、Mathlib の名前でも出さない。順序が合わない主張は、その演習の後に移す。

- 自前実装は「本文の定義と主張」のそのセクションに置く。定義番号のない記述（添字圏の記述、図式をその圏からの関手と見ることなど）も含む。Mathlib が本と違う定義を採っている概念は、2 つの定義の一方から他方を得る主張を、成り立つ向きごとに置く
- Mathlib の名前で述べる主張のうち、対応する Mathlib の補題がそのまま証明になるものは置かず、その補題を `#check` で示す。本の主張がまるごとそれにあたるときは、そのセクションに、主張の 1 文、その補題で済むので宣言を置かないという 1 文、`#check` を置く
- `#check` で示した Mathlib の定義を読者が自分で書くと決めたときは、Mathlib と同じ形で演習にする

### 5.2 名前

宣言の名前は statement の内容から付け、Mathlib の命名規則（定義・構成は lowerCamelCase、定理は snake_case）に揃える。自前実装は本の用語で名付け、Mathlib に末尾の名前が同じ宣言があるときだけ末尾に `'` を付ける。`example` は使わず、ファイル内の通し番号は振らない。

### 5.3 `sorry` にする箇所

自前実装のうち、証明義務がある箇所と、本文が式を与えていない構成を `sorry` にする。

- 構造はフィールドをすべて書き、`sorry` を置かない。演習になるのはその構造を使う宣言のほう
- 本文が式を与えず、主張や証明の中で組み立てる構成（錐の頂点と脚など）は、`:=` 以降をすべて `sorry` にし、型だけ書く

## 6. 完成の確認

作成・編集のたびに次の 3 点を確認する。

- 収録漏れ — 解説資料に出てくる定義・主張・節末問題を列挙し、その一つ一つが、演習ファイルのセクションか、ヘッダの「載せない例と Remark」のどちらかに現れることを確認する
- Lean — `lean_diagnostic_messages` で、`sorry` 以外の警告とエラーがなく、すべての `#check` が解決し、すべての statement が elaborate することを確認する
- 参照 — ファイル内の自前実装の名前を列挙し、名前ごとに、その名前をファイル内で参照している宣言を grep で挙げる。対応する Mathlib の宣言がある名前は、5.1 の、2 つの定義の一方から他方を得る主張以外からの参照が 0 件であることを確かめる
