対象の節: $ARGUMENTS

演習ファイルは、節を読み終えた読者が、その節の定義と主張を自分で Lean に組み直すためのものである。終えたとき、読者はその節の定義と主張を自分で再現しており、その節の概念を以後 Mathlib の名前と形で使える。以下の基準で迷ったときは、この到達点に照らして決める。

着手の条件: 同じ節の解説資料（`.html`）を先に書き、読者に読んでもらってから始める。節をまたぐ取り決めをまとめた [cross-section.md](cross-section.md) を読み、新しい取り決めが生じたら追記する。

## 1. ファイルの構成

情報の置き場所は 4 つに固定する。**どの主張かは宣言の名前、形式化の判断はヘッダの表、主張とその論理構成はセクションの冒頭、Mathlib の対応物は `#check`・`#print`**。散文はセクションの冒頭に限る。

宣言の名前は、本の番号を持つ主張は `<種別>_<番号>`（種別は `def`・`lemma`・`prop`・`thm`・`cor`、節末問題は `ex`。割ったときは末尾に部分を足す）、自前実装は `my` で始まる内容ベースの名前にする。`example` は使わず、ファイル内の通し番号は振らない。

ヘッダは `import` の直後に `/-! -/` で書き、次を順に並べる。

1. 節の数学的な内容は同名の HTML にある、という 1 行
2. 形式化の判断の表。universe の取り方、渡し方（4）、対応物との一致（3）、対応物が特殊ケースや一般化しかないときの範囲の差、対応物がないこと、本にない Mathlib の道具を使った箇所と理由
3. statement を置かない節末問題の一覧。番号と理由を 1 行ずつ
4. 載せない例と Remark
5. 参照した Mathlib のファイル名

セクションの冒頭には、本の主張を 1 文置く。主張の文は、本が定義した形の術語と明示した量化で書き、原文が省いていれば補う。本文にない中間物（補助定義・補題）を立てたときは、続けて `構成:` に中間物と主張の関係を宣言調で書く。`#check`・`#print` の置き方は 3 にある。

大見出し（本文の定義と主張、節末問題）は箱、セクション見出しは本の番号を区切り線で挟む。骨組みは次のとおり。

```lean
import ...

/-! ヘッダ -/

open CategoryTheory ...

-- ╔═════════════════════════════════════════════════════════════════════════
-- ║  本文の定義と主張
-- ╚═════════════════════════════════════════════════════════════════════════

-- ━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
-- 定義 x.y.z
-- ━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
-- 本の主張 1 文。

#check Mathlib.の.対応物

def def_x_y_z ... := sorry
```

コメントは 1 行なら `--`、複数行なら `/- -/`、ヘッダは `/-! -/`。

## 2. 収録

載せるのは、その節の論理展開で役割を持つ定義・主張・節末問題である。定義の直後に地の文で述べられる言い換えや、定義の中に書かれた主張も、役割があれば載せる。例と Remark はこの基準の外にあり、Remark に対応する Mathlib の宣言があるときだけヘッダにその名前を書く。

## 3. 自前実装と Mathlib の使い分け

その節の本文が定義または記述しているものは自前で組み、それ以外は Mathlib のものを使う。

- 自前実装には `my` で始まる名前を付け、本体のそのセクションに置く。定義番号のない記述（添字圏の記述、図式をその圏からの関手と見ることなど）も含む。Mathlib に対応物があれば両者の一致（同値・等式・同型）を示す宣言を置き、以後の宣言は対応物を参照する。`rfl` で済む一致は置かない
- 前の節までに本が定義したものは、Mathlib の名前をそのまま使う
- 本にないものは Mathlib の道具として使う。本にないことと使う理由をヘッダの表に書く

`#check`・`#print` は、読者が節の概念を以後 Mathlib の名前と形で使えるようにするために置く。読者が書く宣言の直前に、対応する Mathlib の宣言を `#check` で示す。本にない Mathlib の宣言は、最初に使う宣言の直前に示す。読者が Mathlib の定義をまだ知らないとき（組んだものと形が違う、または本にない）は `#print` にする。対応物がなければヘッダの表に書く。

## 4. 演習の中身

自前実装を演習にするかは、**中身があるか**で決める。中身とは、書き下ろすと証明義務が残ること、または式や構成を自分で見つける必要があることを指す。中身があれば `sorry` を残して演習にし、なければ `sorry` なしで書き切って渡す。書き切ったものは、本の定義を Lean にしたものとして読者が読んでから演習に入る。

どこまで書いて渡すかは、**中身の所在**で決め、決定と理由をヘッダの表に書く。

- 構造が本の定義の写しに過ぎない — フィールドまで書いて渡す。演習になるのは、その定義を使う主張のほう
- 証明義務を持つ — data を書き、義務だけ `sorry` にする
- 式や構成を見つけること自体が中身 — その部分を `sorry` にする。型は必ず書く

一つの主張に複数の結論が含まれるときは結論ごとに宣言を分け、形式化が重い構成は構成とそれが満たす性質に分ける。読者が同じ分解を作り直さずに済むようにするためである。

## 5. 答えの伏せ方

読者が見つけるべきもの（構成、証明、答えの形）はファイルに置かない。statement や `#check` を読んだ時点で答えの形が分かるものは statement を置かず、置かない理由をヘッダの表に書く。「〜を記述せよ」「〜を特徴づけよ」型の節末問題、Mathlib の宣言名がそのまま答えになる `#check` がこれにあたる。形式化が不自然になる節末問題も statement を置かず、同じ一覧に書く。一部だけ置けるものは、置ける部分を置いたうえで、置かない部分を同じ一覧に書く。

## 6. 完成の確認

作成・編集のたびに次の 3 点を確認し、通ってから完成と報告する。

- 収録漏れ — 解説資料に出てくる定義・主張・節末問題を列挙し、その一つ一つが、演習ファイルの宣言か、ヘッダの「置かない節末問題」の一覧か、「載せない例と Remark」のどれかに現れることを確認する
- Lean — `lean_diagnostic_messages` で、`sorry` 以外の警告とエラーがなく、すべての `#check` が解決し、すべての statement が elaborate することを確認する
- 参照 — 自前実装を参照する宣言があれば、その自前実装に Mathlib の対応物がないことを確かめ、ヘッダの表に書く
