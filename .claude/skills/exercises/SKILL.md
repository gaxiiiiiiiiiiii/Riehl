対象の節: $ARGUMENTS

演習ファイルは、節を読み終えた読者が、その節の定義と主張を自分で Lean で書くためのものである。終えたとき、読者はその節の定義と主張を自分で書いており、その節の概念を以後 Mathlib の名前と形で使える。以下の基準で迷ったときは、読者がこの状態になるほうを選ぶ。

着手の条件: 同じ節の解説資料（`.html`）を先に書き、読者に読んでもらってから始める。節をまたぐ取り決めをまとめた [cross-section.md](cross-section.md) を読み、新しい取り決めが生じたら追記する。

## 1. ファイルの形

骨組みは次のとおり。各部の書き方は 2 以降で上から順に述べる。

```lean
import ...

/-! ヘッダ -/

open CategoryTheory ...

namespace Riehl

-- ╔═════════════════════════════════════════════════════════════════════════
-- ║  本文の定義と主張
-- ╚═════════════════════════════════════════════════════════════════════════

-- ━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
-- 定義 x.y.z
-- ━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
-- 本の主張 1 文。

#check Mathlib.の.対応する宣言

def ... := sorry

end Riehl
```

宣言はすべて `namespace Riehl` の中に置く。大見出しは「本文の定義と主張」と「節末問題」の 2 つ。散文はセクションの冒頭に限る。コメントは 1 行なら `--`、複数行なら `/- -/`、ヘッダは `/-! -/`。

## 2. ヘッダ

`import` の直後に `/-! -/` で書き、次を順に並べる。

1. 節の数学的な内容は同名の HTML にある、という 1 行
2. 載せない例と Remark

## 3. セクション

セクションを置くのは、その節の論理展開で役割を持つ定義・主張・節末問題である。定義の直後に地の文で述べられる言い換えや、定義の中に書かれた主張も、役割があれば置く。例と Remark はこの基準の外にあり、Remark に対応する Mathlib の宣言があるときだけヘッダにその名前を書く。

節末問題のうち、statement を Lean で書くこと自体が解答になるもの（「〜を記述せよ」「〜を特徴づけよ」型）と、形式化が不自然になるものは、セクション見出しだけ置き、冒頭の 1 文を主張の代わりに置かない理由にする。

セクション見出しは本の番号。

## 4. セクションの冒頭

本の主張を 1 文置く。主張の文は、本が定義した形の術語と明示した量化で書き、原文が省いていれば補う。宣言が本の主張とどう対応するかが、名前と statement から読めないときは、続けて `構成:` にその対応を書く。

読者が書く宣言の直前に、対応する Mathlib の宣言を `#check` で示す。本にない Mathlib の宣言は、最初に使う宣言の直前に示す。

## 5. 宣言

### 5.1 名前

宣言の名前は statement の内容から付け、Mathlib の命名規則（定義・構成は lowerCamelCase、定理は snake_case）に揃える。自前実装は本の用語で名付け、Mathlib に末尾の名前が同じ宣言があるときだけ末尾に `'` を付ける。`example` は使わず、ファイル内の通し番号は振らない。

### 5.2 自前実装と Mathlib

その節の本文が定義または記述しているものは自前で定義し、それ以外は Mathlib のものを使う。

- 自前実装は本体のそのセクションに置く。定義番号のない記述（添字圏の記述、図式をその圏からの関手と見ることなど）も含む。対応する Mathlib の宣言があれば両者の一致（同値・等式・同型）を示す宣言を置き、以後の宣言は Mathlib のものを参照する。`rfl` で済む一致は置かない
- 前の節の演習ファイルで自前実装したものも、Mathlib の名前で参照する
- Mathlib のものを使うときは、statement が参照する Mathlib の定義を列挙して読者に示し、読者が選んだものは Mathlib と同じ形で自前に書く。以後の宣言は Mathlib のものを参照する
- Mathlib に対応する宣言がないものは、本の定義で自前実装する

### 5.3 `sorry` にする箇所

自前実装のうち、証明義務がある箇所と、式や構成を読者が決める箇所を `sorry` にする。どちらもない定義は `sorry` なしで書き、読者はそれを本の定義として読んでから演習に入る。

- 本の定義と同じフィールドを持つ構造は `sorry` なしで書く。演習になるのはその定義を使う主張のほう
- data は書き、証明義務だけ `sorry` にする
- 式や構成を読者が決めるときは、その部分を `sorry` にし、型は書く

一つの主張に複数の結論が含まれるときは結論ごとに宣言を分け、形式化が長くなる構成は、構成を与える宣言とそれが満たす性質の宣言に分ける。読者が同じ分割を作り直さずに済むようにするためである。

## 6. 完成の確認

作成・編集のたびに次の 3 点を確認し、完成の報告にそれぞれの結果を 1 行で書く。

- 収録漏れ — 解説資料に出てくる定義・主張・節末問題を列挙し、その一つ一つが、演習ファイルのセクションか、ヘッダの「載せない例と Remark」のどちらかに現れることを確認する。報告には列挙した項目数と不足の数を書く
- Lean — `lean_diagnostic_messages` で、`sorry` 以外の警告とエラーがなく、すべての `#check` が解決し、すべての statement が elaborate することを確認する。報告には残っている警告の種類を書く
- 参照 — ファイル内の自前実装の名前を列挙し、名前ごとに、その名前をファイル内で参照している宣言を grep で挙げる。対応する Mathlib の宣言がある名前は、一致を示す宣言以外からの参照が 0 件であることを確かめる。報告には名前ごとの参照件数を書く
