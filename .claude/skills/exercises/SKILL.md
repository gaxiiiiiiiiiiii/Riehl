対象の節: $ARGUMENTS

演習ファイルは、**その節が導入する定義と主張を、ユーザーが自分で組み直せる形に並べたもの**です。迷ったときはこの目的に照らしてください。節の中心的な概念が演習として残らない結論になったら、その判断は誤りです。

同じ節の解説資料（`.html`）を先に書き、ユーザーに読んでもらってから着手する。書く前に、節をまたぐ取り決めをまとめた [cross-section.md](cross-section.md) を読む。新しい取り決めが生じたらそこに追記する。

書式の実物は `Riehl/Ch2_Yoneda/Yoneda.lean` にある。新しい演習ファイルを書く前に読む。

作成・編集したら2つ確認する。

**収録漏れ** — 解説資料に出てくる定義・主張（番号の有無を問わない）・節末問題を列挙し、その一つ一つが、演習ファイルの宣言か、ヘッダの「statement を置かない節末問題」の一覧か、「載せない例と Remark」のどれかに現れることを確認する。どこにも現れない項目があれば収録漏れ。elaborate するかどうかの検証では、この漏れは見つからない。

**Lean** — `lean_diagnostic_messages` で、`sorry` 以外の警告とエラーが無いこと、すべての `#check` が解決すること、すべての statement が elaborate することを確認する。証明が `sorry` のまま残っている状態を「完成」と報告しない。

## ファイルの構成

演習ファイルは statement を本の順に並べたものです。解く人は同名の解説資料（`.html`）を読んでからこれを開きます。情報の置き場所を次のように固定してください。**どの主張かは宣言の名前、形式化の判断はヘッダの表、主張とその論理構成はセクションの冒頭、Mathlib の対応物は `#check`** です。この4つ以外に散文を置かないでください。

ファイルの要素は次の4つです。

1. **import** — ファイルの先頭
2. **ヘッダ** — `import` の直後に `/-! -/` で書く（先頭に置くと Mathlib のヘッダリンタと衝突する）。次の順に並べる
   - 節の数学的な内容は同名の HTML にある、という1行
   - **形式化の判断**（表）。Set 値関手の universe の取り方、`my` 定義をどこまで書いて渡すか、Mathlib のパッケージングとの差、対応物が特殊ケースや一般化しかないときの範囲の差、対応物がないことの明示
   - **statement を置かない節末問題**（一覧）。番号と、置かない理由を1行ずつ。一部だけ置かないものもここに書く
   - 載せない例と Remark。Remark に対応する Mathlib の宣言があればその名前
   - 参照した Mathlib のファイル名
3. **前提**（`namespace Recap`）— 演習を解くのに必要だが、その節が導入するのではない知識を Mathlib から写す。前の節までに出た定義、`statement` が暗黙に依存する instance 由来の構造（`ℕ` を圏にする `Preorder.smallCategory`、`Mat R` の圏構造など）が対象。各写しには1行の見出しコメントを付ける。**その節が導入する定義は、原則としてここに写さず本体に置く**（例外は下記「一致するか食い違うか」）
4. **本文の定義と主張** と **節末問題** — 本の主張ごとにセクションを作り、出現順に並べる

見出しは2階層です。大見出し（`前提` / `本文の定義と主張` / `節末問題`）は箱で囲み、セクション見出しは本の番号にします。箱の右端は閉じないでください（全角の字送りはフォント依存なので、右端を揃えると環境によってずれます）。

セクションの冒頭に置くのは次の2つだけです。ファイル中の散文はここに限ります。

- **主張1文** — 本のその主張。解説資料の再掲ではなく、下の statement を本の主張として読める程度に書く
- **`構成:`** — 一つの主張を複数の宣言に割ったときだけ置く。論理構成だけを宣言調で書く（「Ψ : Fc → Hom(C(c,−), F) を構成し、それが……を示す」）。割った理由、形式化の都合、証明の方針は書かない。宣言が1本のセクションには置かない

宣言の直前には `#check` だけを置き、コメントは置きません。

コメントは、1行で済むなら `--`、複数行になるなら `/- -/` で書きます。見出しと罫線は `--` です。`/-- -/`（doc コメント）は使いません。`/-! -/` はファイル冒頭のヘッダだけです。

本文中の例と Remark は載せません（statement も `#check` も置かない）。載せるのは定義・本文の主張・節末問題です。主張は番号の有無で判断しないでください。定義の直後に地の文で述べられる言い換え（「C が始対象を持つ ⟺ 定数関手が表現可能」など）も本文の主張なので載せます。Remark に対応する Mathlib の宣言があるときだけ、その名前をヘッダに注記してよい（1.7 の 2-圏、2.2 の注意2.2.7 など）。

## 演習の作り方

- **一致するか食い違うか**は、同じ概念を指すかではなく、**データの持ち方が同じか**で判定する。圏論の概念はたいてい Mathlib にもあるので、概念で判定すると常に「一致」に倒れ、演習が消える
  - **食い違う** — 持ち方が違う。本の定義2.1.4 は「対象 c と自然同型 C(c,−) ≅ F の組」、Mathlib の `CorepresentableBy` は「hom の全単射の族＋合成との両立条件」。本の定義1.5.4 は F, G, η, ε だけ、Mathlib の `Equivalence` は三角等式込み。この場合は `my` で始まる名前で自前実装し、**本体に置く**。以降の演習の statement は Mathlib のもので述べる
  - **一致する** — 持ち方まで同じ。定義1.5.7 の充満・忠実は Mathlib の `Full`・`Faithful` と同じ内容の `Prop`。この場合だけ Recap に写し、statement では Mathlib のものを使う
  - 迷ったら食い違う側に倒す。自前実装が1つ増えるだけだが、逆に倒すと節の主題が演習から消える
- `my` 定義は組むこと自体が演習であり、それ以降の演習の statement には使わない（Mathlib のものを使う）。例外は自前定義の直接の帰結を組み上げる場合（補題1.7.1 の縦合成から系1.7.2 の関手圏を組む、2.2 の Ψ から右逆・左逆を述べるなど）だけ
- `my` 定義をどこまで書いて渡すかは、**その定義の中身がどこにあるか**で決める。決定と理由はヘッダの表に書く
  - **構造が本の定義の写しに過ぎない** — 1.5 の `MyEquivalence`、2.1 の `MyRepresentation`。`structure` をフィールドまで書いて渡す。演習になるのは、その定義を使う主張のほう
  - **proof obligation を持つ** — 1.7 の縦合成・水平合成。data を書き、`naturality` などの証明義務だけ `sorry` にする
  - **式や構成を見つけること自体が中身** — 2.2 の Ψ。丸ごと `sorry` にする
  - 型ごと `sorry`（`def f : Type := sorry`）にはしない。本の定義の形が渡らないうえ、universe だけがヒントとして残る
- 形式化が重い構成は、構成と、それが満たす性質に分けて置く。一つの `Equiv` や `∃!` にまとめると、解く側が同じ分解を自分で作り直すことになる
- 一つの主張に複数の結論が含まれるものは、結論ごとに宣言を分ける。どこを分けたかはセクション冒頭の `構成:` と、各宣言の名前で示す
- すべての演習に名前を付ける。`example` は使わない。本の番号を持つ主張は番号ベース（`prop_2_2_3`・`thm_2_2_4_right_inv`・`cor_2_2_8_yoneda_full`・`ex_2_2_i_left_inv` など）、`my` で始まる自前定義は内容ベースにする
- ファイル内の通し番号は振らない。演習を指すのは本の番号で行う
- すべての演習に、**その statement に対応する** Mathlib の定理・定義の `#check` を `@` 付きで添える（`@` なしは暗黙引数が畳まれ、実在確認が甘くなる）。`#check` は宣言の直前に置く。対応物がない場合は `#check` を置かず、ヘッダの表に「Mathlib に対応物なし」と書く。特殊ケースや一般化しかないなど対応が部分的な場合は、その `#check` を付けたうえで範囲の差をヘッダの表に書く
- `#check` が指すのは、**その statement と型が対応する** Mathlib の宣言だけ。証明の途中で使う道具は指さない。両方に読めるものは、statement 全体に対応していれば対応物、そうでなければ道具
- `#check` の名前が答えになる場合は置かない。「C(−,c) の部分関手を特徴づけよ」に対する `Sieve` のように、Mathlib の宣言名そのものが答えであることがある。置かなかったことはヘッダの表に書く
- 節末問題は原則すべて載せる。ただし **statement を書くと答えの形が出てしまう問題は置かない**。「〜を記述せよ」「〜を特徴づけよ」型は、求める対象や条件が型や式に現れるので原則こちら。判定基準は「まだ解いていない人がその statement を読んで、答えの形を知ってしまうか」。形式化が不自然なものも同じく置かない。置かない番号と理由はヘッダの一覧に書く。一部だけ形式化できるものは、できる部分を置いたうえで、置かない部分を同じ一覧に書く
- リンタの警告は、ファイルの書き方で解決する。`set_option` や `lakefile.toml` でリンタを無効化して黙らせない。唯一の公認例外は `linter.style.header`（Mathlib の copyright ヘッダ要求。LICENSE を持たない個人プロジェクトに適合しないため lakefile で無効化済み）
- Hint、証明方針、道具の `#check` は書かない（証明は自力）
- 本の主張そのものの解説は解説資料の担当なので、演習ファイルで書き直さない
