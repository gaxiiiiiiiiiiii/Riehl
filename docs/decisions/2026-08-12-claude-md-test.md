## 評価

`CLAUDE.md` は内容面の規定としては機能した。欠けているのは形式面で、上の「割れた点」7項目がそのまま不足箇所である。

## 決定

上の「割れた点」7項目について決めたこと。`CLAUDE.md` にはここから規定だけを短く写す。

1. **宣言の形式** — 原則 `example`。後で使う可能性があるものだけ名前を付ける。理由は、演習の主張には Mathlib に対応物があるので、以降の節ではそちらを使えばよく、演習はその場限りの証明で構わないため。ファイルを跨いで参照したい場面が出たら、そのときに別途対応を考える
2. **命名規則** — 併用。`my` で始まる自前定義は内容ベース、番号を持つ主張に名前を付ける場合は本の番号ベース。あわせて、`example` の演習にも本の定理番号・演習番号をコメントに書く
3. **通し番号** — 振らない。ファイル内の通し番号は持たず、本の番号だけで指す
4. **namespace** — `namespace Riehl` で全ファイルを囲む。節をまたいで同名の `my` 定義を作ったときに衝突するのを避けるため。後から足すほうが高くつくので最初から入れる
5. **コメント書式** — `--` の行コメントと罫線（master 式）。`/-! -/` や `/-- -/` は使わない
6. **本文の例** — 拾わない。定義・命題・節末問題だけを載せる
7. **演習の粒度** — 主張ごとに分割する。分割した各演習には、本のどの主張のどの部分か（「定理1.5.9 の順方向のうち忠実性」など）をコメントで示す

2. **答えを statement に書いてよいか** — 規定を置かない。一般則にすると、どちらに倒しても外れる問題が出る。ファイルごとの判断に任せ、気になったら個別に直す
3. **Recap の線引き** — 本文で導入される定義は `my` で始まる名前で自前実装する。演習の statement は Mathlib の定義で書く。Recap には、教科書が明示的には扱わないが演習を解くのに必要な前提知識だけを置く。この基準では、定義1.5.7 は自前実装が正しく（1回目・2回目とも抜けている）、`IsConnected` まわりは Recap が正しい（2回目の判断が当たり）

### 残った点

1. **リンタの回避** — `set_option linter.style.header false` をファイル先頭に入れ、「ヘッダリンタが全コマンドに警告を出す」と報告してきた。当該行を削ったコピーを `lake env lean` でコンパイルして確認したところ、header 系の警告はゼロだった。報告は誤りで、この行は不要。2回目の `lakefile.toml` 書き換えと合わせて、2回続けて設定でリンタを黙らせている
2. **`MyEquivalence` を statement に使う箇所** — 命題1.5.13、注意1.5.17、同値不変性は `MyEquivalence` で述べられていた。規定は「statement は Mathlib の定義で書く」だったが、本の意味の同値についての主張なので自前定義で述べるほうが忠実。生成物のほうが正しく、規定の文言が追いついていなかった

### 決定

1. **リンタを黙らせない** — 警告はファイルの書き方で解決する。`set_option` や `lakefile.toml` での無効化はしない
2. **statement の規定を精密化** — 本文の定義と Mathlib の定義が一致する概念は Mathlib のもので述べ、食い違う概念は自前定義で述べる
3. **形式化が重い構成は分けて置く** — 一つの `Equiv` や `∃!` にまとめない。master の 1.5 を実際に解いた経験から出た。master 版は補題1.5.1 を構成・制限2本・逆向きの4つに分けており、そちらは解き進められたが、3回目の1本の `Equiv` は解く側が同じ分解を作り直すことになる。テストでは出ず、解いて初めて分かった
4. **4回目は回さない** — 収束しており、残る2点は追試なしで決められる。1.5 だけで回し続けると `CLAUDE.md` が §1.5 に過適合する。次の情報は別の節（2.1）を書いたときに得られる
5. **master の 1.5 は差し替えない** — 既に補題1.5.1 まわりを解き始めており、`myNatTransOfFunctor` は作業中。3回目の生成物には master の4分解に対応する宣言がないので、解答の移植先がない。新しい規定は 2.1 以降のファイルから適用する
