# 2026-08-21 自前実装の判定軸を2つに分けた(対象 2.2)

§2.2 の定理2.2.4 を組み直す過程で、`/exercises` skill の「一致するか食い違うか」の判定が、独立した2つの問いを1つにまとめていることが判明した。判定を2段に分けた。

## 症状

規約は「データの持ち方が Mathlib と食い違えば `my` で自前実装して本体に置く、一致するなら Recap に写して statement では Mathlib のものを使う」と書いていた。これを文字どおり適用すると、次の2件が Recap に落ちて演習から消える。

- **2.2 の Ψ** — Mathlib の `coyonedaEquiv.symm` と持ち方まで同じ。だが `Ψ(x)_d(f) := Ff(x)` を自然性から導くことが §2.2 の核心で、これを写しにすると節の主題が消える
- **2.2 の `evaluation`** — Mathlib の `evaluation C D` と data は同じ。だが関手性と `map` の自然性という証明義務を持ち、しかも注意2.2.7 がこの節で導入する概念

Ψ については規約本文の中で既に矛盾していた。「一致するなら Recap」と書く一方、「どこまで書いて渡すか」の項は「式や構成を見つけること自体が中身なら丸ごと `sorry`」の例として Ψ を挙げ、演習扱いを前提にしていた。

## 原因

「Mathlib と一致するか」という単一の軸が、本来独立な2つの問いを兼ねていた。

- その定義を**組むこと自体**を演習にするか
- **statement** をどちらの定義で述べるか

前者は構成に中身があるかの問題で、Mathlib に同じものがあるかとは無関係。後者は下流の一貫性の問題で、持ち方が同じなら Mathlib のものに寄せるのが正しい。1つの軸にまとめると、持ち方が同じものは自動的に演習から外れる。

## 変更

`/exercises` skill の「一致するか食い違うか」を、問い1（組むこと自体を演習にするか）と問い2（statement をどちらで述べるか）の2段に分けた。問い1の判定基準は「構成に中身（証明義務、または式や構成の発見）があるか」で、Mathlib に同じものがあるかは問わない。

両方を通ると「組むのは演習、statement は Mathlib のもの」という組み合わせが生じる。Ψ と `evaluation` がこれに当たる。既存の「`my` 定義は以降の statement には使わない」という項と整合する。

中身がない側の例として `Functor.rightOp` を挙げた。`op` の付け外しだけで関手則も自動に閉じる。

## 判定が変わらないもの

1.5 の `MyEquivalence`(三角等式の有無で持ち方が違う)、1.7 の縦合成・水平合成(proof obligation を持つ)、1.5 の `Full`・`Faithful`(持ち方が同じで中身もない)は、いずれも結論が変わらない。理由付けが2段になるだけ。

## 2. SKILL.md から判定済みの実例を落とした

上の修正を入れた直後、実例が判定の本体になっているという指摘を受けた。実際、判定基準は各分岐1行なのに実例が2〜3行あり、76行中10行が節番号を含んでいた。新しい節を作るときにそこへ一致する実例がなければ、一般化する材料がない。基準ではなく記憶になっていた。

公式ガイド(code.claude.com/docs/en/skills)の「State what to do rather than narrating how or why」「Keep SKILL.md under 500 lines. Move detailed reference material to separate files」に反してもいた。長さではなく、中身が「何をするか」ではなく「過去にどう判定したか」になっていた点が問題。

節番号と本の主張への言及を SKILL.md から全て落とし、判定条件だけを残した。

- 問い1の「中身がある」を、proof obligation を持つか、data の式・構成を自分で見つける必要があるか、と定義した。中身なしの側は「書き下ろしても義務が自動で閉じ、式に選択の余地がない」
- 問い2の「持ち方が同じ」を、何をデータとして持ち何を条件として持つかまで一致すること、フィールドの増減があれば食い違う、と定義した
- 名前の規則を実例列挙から `<種別>_<番号>` の形に置き換えた
- 「どこまで書いて渡すか」の3分岐から実例を落とし、後者2つを兼ねる場合の扱いを1行足した

判定済みの実例は各成果物のヘッダと `docs/decisions/` にあるので、4つ目の写しは作らない。書式の実物は `Riehl/Ch2_Yoneda/Yoneda.lean` を読む、という既存の1行が実例への入口になっている。

## 3. 自前定義の参照を Mathlib 優先に統一した

2.2 の `myCoyonedaLemma` を組むとき、成分に自前の全単射(演習、`sorry` を含む)を渡してしまった。未証明の宣言に下流が依存し、自然性を正しく証明しても宣言として完成しない状態になる。

規約側には「`my` 定義はそれ以降の演習の statement には使わない。例外は、その自前定義の直接の帰結をすぐ次に組み上げる場合だけ」とあったが、この例外条項が曖昧で、実際その解釈で正当化していた。また「statement には使わない」としか書いておらず、本体での参照を素通ししていた。

**他の宣言から参照するのは原則 Mathlib のもの、自前定義を参照してよいのは Mathlib に対応物がない場合だけ、statement と本体で同じ**、に統一した。判定軸が「Mathlib に対応物があるか」となり、statement をどちらで述べるかの判定(問い2)と同じ軸になる。

検討の途中で「`sorry` を含む宣言は参照しない」という案を出したが却下された。対応物があるのに完成した自前定義を参照してよいことになり、Mathlib 優先の原則が崩れる。

検証手順に「自前定義が他の宣言から参照されていないこと」を1項目足した。

1.5 の `myInverseMap`・`myInverseMap_spec` は、Mathlib に単独の対応物がないため参照が許される側。過去の演習ファイルは様式が発展途上で演習としての役割は果たしているので、遡って直さない。
