対象の節: $ARGUMENTS

## これは何か

テキストの副読本です。読者はテキストを読みながら、その節の定義と定理を Lean で自分の手で組み直します。出典はテキスト（所在は CLAUDE.md にある）。同じ節の解説 HTML は兄弟であって、こちらの出典ではありません。

ファイルの中身は2種類しかない。**本がこの節で述べていること → 演習（`sorry`）。それを支えるもの → `sorry` にせず書く。** 定義なら、この節が導入する定義が前者、この節が導入せずに使う概念が後者。主張は前者。Mathlib の語彙は後者。

書く前に、節をまたぐ取り決めをまとめた [cross-section.md](cross-section.md) を読む。新しい取り決めが生じたら追記する。書式・命名・ヘッダの表・`#check`・universe の扱いは、直前の節の演習ファイルに倣う（そこに現れている流儀は以下で改めて指示しない）。まだ節が一つもなければ、下記の規則だけに従う。

## 収録

読者がテキストの議論を追いながら組むためのものなので、その節の**論理展開で役割をもつ**定義・主張・演習問題を、出現順に置く。番号の有無は問わない（定義の直後に地の文で述べられる主張も対象）。載せるかどうかはテキストの議論での役割で決めるのであって、機械的な分類では決めない。

- 本文中の例と Remark は載せない
- 前の節までに演習として扱ったものと中身が同じ主張は置かない（どこで扱ったかをヘッダに書く）
- 定義を展開するだけで成り立つ主張は置かない（その旨をヘッダに書く）
- テキストが対象範囲の外の節の結果を引くなら、それを使う直前に演習として置く
- statement を書くと答えの形が出てしまう演習問題は置かない（「〜を記述せよ」「〜を特徴づけよ」型。置かない番号と理由をヘッダに書く）。一部だけ形式化できるものは、できる部分を置いたうえで置かない部分を同じ一覧に書く

## statement

**テキストの主張と1対1に対応させる。** statement はその節の主張そのもので、読者が解くべき問題です。変えてよいのは述べる**語彙**（Mathlib の名前）と universe だけで、主張の**内容と形**は変えません。

次をしない。どれも、読者にテキストとは別の問題を解かせることになる。

- 主張を強める・弱める
- 証明の途中形（補題や中間ステップ）に置き換える
- Mathlib の既存宣言の型に寄せて、主張の一部を落とす

一つの主張を複数の宣言に割るのは、主張自身が複数の部品や結論をもつときだけ。割る単位は**主張の構造**であって、証明の手順ではない。形式化が重い構成は、構成と、それが満たす性質に分けて置く（一つの `Equiv` や `∃!` にまとめない）。

## 定義

読者が定義を自分の手で組むために、この節が導入する定義は `my` で始まる名前で自前に実装し、本体に置く。これが演習。`#check` は Mathlib の対応物の注記であって、定義の代わりにはならない。

定義を学ぶために `my` の形で書き写し、中の証明項を演習として `sorry` にする。

自前実装は演習なので、以降の主張からは参照しない。主張は Mathlib の宣言で述べる。Mathlib に**同じデータの持ち方**の対応物がない（何をデータとし何を条件とするかが違う、フィールドの増減がある）ときだけ、自前実装で述べる（Mathlib の持ち方に寄せると主張の形が変わるため）。迷ったら自前実装で述べる側に倒す。

**前提**（`namespace Recap`）には、読者が解くときに参照するために、この節が導入せずに使う概念を Mathlib から書き写す。演習ではないので証明項も `sorry` にせず、そのまま写す。各写しに1行の見出しコメントを付ける。前の節で演習にした `my` 定義は写さず、その節を import して使う。

本がこの節で導入していない概念を、あえて演習にしたいことがある。これに規則はない。書き手が候補だと思ったらユーザーに確認し、決めた理由をヘッダの表に書く。

## 書かないこと

証明。`sorry` にして読者に残す。Hint・証明方針・道具の `#check`・難易度の示唆も書かない（どれも読者が自分で見つけるもの）。本の主張そのものの数学的な解説（これは演習の仕事ではない）も書かない。

## 形式

情報の置き場所を固定する。**どの主張かは宣言の名前、形式化の判断はヘッダの表、主張とその論理構成はセクションの冒頭、Mathlib の対応物は `#check`。** この4つ以外に散文を置かない。

ファイルの要素は次の順。

1. **import**
2. **ヘッダ** — `import` の直後に `/-! -/` で書く（先頭に置くとリンタと衝突する）。次を並べる: 節の数学的内容の所在の1行／**形式化の判断**（表。universe の取り方、自前実装のどこを空けたか、Mathlib のパッケージングとの差、対応が部分的なときの範囲差、対応物がないことの明示。主張の形の変更はここに書けない――形は変えないため）／**収録しなかったもの**（前の節で扱い済み・展開するだけ・statement が答えになる演習問題、それぞれ理由を1行）／載せない例と Remark（Remark に対応する Mathlib 宣言があればその名前）／参照した Mathlib ファイル名
3. **前提**（`namespace Recap`）— 中身は「定義」の節のとおり
4. **本文** — 定義・主張・演習問題を出現順に。演習問題が節の末尾にまとまっている本では、本文と節末問題の2区画に分ける。演習問題が本文中に番号付きで現れる本では区画を分けず、本文の出現順にそのまま並べる

見出しは2階層。大見出し（前提／本文／節末問題）は箱で囲み、セクション見出しは本の番号にする。箱の右端は閉じない（全角の字送りがフォント依存でずれるため）。

セクション冒頭に置くのは次の2つだけ。ファイル中の散文はここに限る。

- **主張1文** — 本のその主張。下の statement を本の主張として読める程度に書く
- **`構成:`** — 一つの主張を複数の宣言に割ったときだけ置く。割った部品を宣言調で並べる（割った理由・証明方針・形式化の都合は書かない）。宣言1本のセクションには置かない

宣言の直前には `#check` だけを置く。`#check` はその statement と型が対応する Mathlib の宣言を `@` 付きで添える（証明の途中で使う道具は指さない）。対応物がなければ置かず、ヘッダに書く。名前が答えになる場合は置かず、置かなかったことをヘッダに書く。部分的な対応しかないときは `#check` を付けたうえで範囲の差をヘッダに書く。ヘッダの表で Mathlib の宣言名に言及したなら、その宣言に `#check` を添える（名前を挙げておいて `#check` を置かない、はしない）。

すべての宣言に名前を付ける（`example` は使わない）。本の番号をもつ主張は `<種別>_<番号>`（割ったときは末尾に部分を足す。種別は `def`・`lemma`・`prop`・`thm`・`cor`、演習問題は `ex`）、`my` で始まる自前実装は内容ベース。ファイル内の通し番号は振らない。

コメントは1行なら `--`、複数行なら `/- -/`。見出しと罫線は `--`。doc コメント（`/-- -/`）は使わない。`/-! -/` はヘッダだけ。

リンタの警告はファイルの書き方で解決する。`set_option` や `lakefile` で黙らせない（唯一の例外は `linter.style.header`。lakefile で無効化しておく）。

## 検証

- **忠実性** — 各宣言を、対応するテキストの主張に突き合わせる。主張の内容が落ちていたり形が変わっていたりしないこと。収録漏れは、テキストの項目を列挙して各項目が宣言・ヘッダのどれかに現れることを確認する（elaborate の検証では漏れは見つからない）
- **定義** — この節が導入する定義のすべてに、本体の `my` 実装があること。`#check` だけで済ませた定義がないこと
- **Lean** — `lake build`（lean-lsp MCP があれば `lean_diagnostic_messages`）で `sorry` 以外の警告とエラーが無いこと、すべての `#check` が解決すること、すべての statement が elaborate すること。`sorry` のまま「完成」と報告しない
- **参照** — 自前実装が以降の主張から参照されていないこと（Mathlib に同じ持ち方の対応物がない場合を除く）
